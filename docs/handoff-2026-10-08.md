## 先認識系統

前端是 React／Vite；`src/App.tsx` 管首頁、路由與漂浮算力球，`src/components/layout/` 管共用導覽；`server.ts` 是 Express 網站 API。`/gpus` 結合清冊、Prometheus、exporter 與 TCP 存活探測；歷史圖由 `tools/history-service.ts` 定期寫 SQLite；成員帳號與頭像由 `member-service.ts` 和獨立 PVC 管理。叢集快照由映像中的 `cluster-status.default.json` 提供，顯示盤點日期，不可當即時數值。成員可登入 `/member/me` 自行更新公開檔案；管理入口 `/admin/members` 只使用 `ADMIN_PASSWORD` 環境變數，沒有預設密碼。

線上在 Kubernetes `default` namespace：`hpc-lab-site` 為 2 replicas，`hpc-lab-history` 與 `hpc-lab-members` 各 1 replica。網站使用 `pokai516/hpc-lab:latest` 且 `imagePullPolicy=Always`；另兩個服務可能停留在各自最後一次 rollout 的 digest，**不要只看 tag，應看 Pod `imageID`**。網站舊 hostPath `/app/data` 保存聯絡資料；歷史和成員資料則在 `hpc-lab-history`、`hpc-lab-members` PVC。PVC 是 `local-path`，與所在節點綁定；不要因 Pod 重建而刪除 PVC。

## 接手者第一次操作

1. 取得 GitHub 讀寫權限、Docker Hub `pokai516/hpc-lab` 的映像推送權限，以及原管理者私下交付的網站專用 kubeconfig。閱讀[架構書](website-architecture.md)與交接包中的 `config/live-state-redacted.json`。學長可自行部署網站；原管理者保留叢集與資料管理。Docker Hub 權限需由原管理者在 Docker Hub 另行授予，交接包不含登入密碼。
2. 安裝 Node.js 20、Docker、`kubectl`、Python 3，並在自己的工作目錄執行：

   ```powershell
   git clone git@github.com:Uokio516/tunghai-hpclab-website.git
   Set-Location tunghai-hpclab-website
   npm ci
   Copy-Item .env.example .env
   npm run dev
   ```

   `.env` 只供本機，內容由管理者另給；沒有監控服務連線時，本機 `/api/gpus` 可能回 503，這不代表前端版型故障。不要把 `.env`、kubeconfig 或私鑰加入 commit。
3. 先做一個不部署的練習：修改 `src/data/` 的展示文字，在瀏覽器確認，再執行 `npm run lint`、`npm run build`、`npm run test:members`。監控程式變動另跑 `node tools/verify-gpu-monitoring.mjs`。確認 `git diff` 只包含預期變更。
4. 修改清冊時依 `tools/README.md` 的腳本順序產生兩份 `*.default.json`；**不要使用**舊的 `tools/collect-cluster-status.sh`，也不要直接寫入線上 hostPath。改 exporter 前先看 `tools/exporters/README.md` 與現有覆蓋缺口。

## 人工部署與驗證

目前沒有已確認的自動部署流程。程式 push GitHub **不會**自行更新線上網站。學長提交 PR 並完成測試後，可使用網站專用憑證自行執行正式部署；原管理者仍負責叢集管理。操作如下：

```powershell
npm ci
npm run lint
npm run build
npm run test:members
docker build -t pokai516/hpc-lab:latest .
docker push pokai516/hpc-lab:latest
$kube = 'C:\path\to\hpc-lab-deployer.kubeconfig'
kubectl --kubeconfig $kube rollout restart deployment/hpc-lab-site -n default
kubectl --kubeconfig $kube rollout status deployment/hpc-lab-site -n default --timeout=180s
kubectl --kubeconfig $kube get pods -n default -l app=hpc-lab -o custom-columns='NAME:.metadata.name,READY:.status.containerStatuses[0].ready,IMAGEID:.status.containerStatuses[0].imageID'
```

若更動 `member-service.ts`，先 rollout `hpc-lab-members` 並驗證，再 rollout 網站；若更動 `tools/history-service.ts`，也須 rollout `hpc-lab-history`。核對每個更新的 Pod `imageID` 與新推送的 Docker digest 相同，然後檢查 `/`、`/people`、`/gpus`、`/api/members/public` 與歷史 API。發布前記下三個 Deployment 的既有 digest，以供回復；不要以 `rollout undo` 搭配可變的 `latest` tag 當成可靠回復。`k8s-deploy.yaml` 是過時參考，不能直接覆蓋線上 Deployment。網站 Pod selector 是 `app=hpc-lab`，不是 deployment 名稱。若失敗，先回到已驗證的舊 digest；不要刪除資料卷。

## 重新備份與還原

**原管理者至少在每次部署前、每次成員帳號調整後做備份**，並另外安排定期備份及異地保存。`tools/backup-sqlite.cjs` 使用 SQLite 線上備份 API，能把 WAL 中已提交的資料放進單一一致的 `.sqlite` 檔。不要只複製執行中的主檔。使用方法是先用 `kubectl get pods` 找目前的 Pod，再把腳本複製到 Pod 的 `/tmp`；下例示範成員服務：

```powershell
$kube = 'C:\path\to\hpc-lab-deployer.kubeconfig'
$pod = kubectl --kubeconfig $kube get pods -n default -l app=hpc-lab-members -o jsonpath='{.items[0].metadata.name}'
kubectl --kubeconfig $kube cp tools/backup-sqlite.cjs "default/${pod}:/tmp/backup-sqlite.cjs"
$stamp = Get-Date -Format yyyyMMdd-HHmmss
kubectl --kubeconfig $kube exec -n default $pod -- node /tmp/backup-sqlite.cjs /app/members/members.sqlite "/tmp/members-$stamp.sqlite"
kubectl --kubeconfig $kube cp "default/${pod}:/tmp/members-$stamp.sqlite" "members-$stamp.sqlite"
kubectl --kubeconfig $kube cp "default/${pod}:/app/members/avatars" "avatars-$stamp"
```

在 Windows 上執行 `kubectl cp` 時，先 `Set-Location` 到備份目錄，用上例的**相對目的路徑**；`C:\...` 的冒號可能被 `kubectl cp` 當成遠端路徑。歷史服務的來源是 `/app/history/metrics.sqlite`，網站聯絡表單的來源是 `/app/data/database.sqlite`；兩者也使用相同步驟，但分別從 `app=hpc-lab-history` 與 `app=hpc-lab` Pod 取得。網站 hostPath 若分散到不同節點，應逐一確認各節點資料；此交接快照的兩個網站 Pod 在同一節點。

備份完成後，對每份 SQLite 執行 `PRAGMA integrity_check` 並確認結果是 `ok`，再用 `Get-FileHash -Algorithm SHA256` 建校驗清單。交接包本身已有驗證過的 `SHA256SUMS.txt`。要**還原**時，先確認使用的是哪份備份與哪個叢集，安排維護時段，停掉相應服務的寫入者，把成員 SQLite／頭像、歷史 SQLite 分別放入對應 PVC，把聯絡 SQLite 放回正確 hostPath，檢查檔案權限與完整性後才重新啟動。不要在服務運作時覆寫主檔；不要把 `legacy-cluster-status.json` 覆蓋映像內的較新快照。若要在全新叢集重建，先依現有 manifests 建立 PVC 和服務，另用一次性的維護 Pod 掛載各 PVC 匯入資料。還原演練應在隔離環境完成，不直接拿正式資料庫試錯。

Git 歷史可用 `git clone <交接包>/source/website-git.bundle new-website` 復原；Docker 映像可用 `docker load -i <交接包>/source/hpc-lab-image.tar` 載入。此交接包是單次快照，不會隨線上資料自動更新。

## CI/CD 是什麼、能省掉哪些操作

CI（持續整合）是在每次提交或 PR 自動執行 `npm ci`、型別檢查、建置與測試；CD（持續部署）是在通過後建置映像、推送並更新 Kubernetes。目前學長可用受限憑證手動部署；原管理者保留叢集管理權。若日後用 GitHub Actions 部署，可把 Docker Hub 登入與**權限受限**的部署憑證保存在 GitHub Actions Secrets，讓學長從工作流程啟動發布。建議使用 commit 對應的不可變映像 tag 或 digest，在流程最後比對 Pod `imageID`。

CI/CD **不會取代** PVC 備份、資料還原、叢集升級、Secret 輪替、硬體 exporter 維護與故障排除；這些仍要有人負責。目前 repo 尚無已驗證的自動部署工作流程，也沒有可確認的定期 PVC 備份，不能假設 `git push` 就等於部署或備份。

## 部署憑證交付與撤銷

原管理者已在 `default` namespace 建立 `hpc-lab-deployer` ServiceAccount、同名 Role／RoleBinding，規則在 `tools/hpc-lab-deployer-rbac.yaml`。實測可操作網站三個 Deployment，不能讀取 Secret、刪除 PVC 或修改其他 Deployment。`private/hpc-lab-deployer.kubeconfig` 連至 `https://140.128.101.193:6443`，只需這一個檔案；傳送時使用加密的私下通道。學長還需由原管理者另授 Docker Hub 映像推送權限，才能完成 `docker push`。部署前先用 `kubectl --kubeconfig <檔案> get deployment hpc-lab-site -n default` 測試連線。

若停止授權，原管理者用完整管理 kubeconfig 刪除 `hpc-lab-deployer-token` Secret，該 kubeconfig 即失效；如要重新授權，再由原管理者產生新 token 與 kubeconfig。此憑證為長效 ServiceAccount token，應像密碼一樣保管。學長的發布操作應只涉及映像與 rollout，資料備份、PVC 還原、Secret、叢集設定仍由原管理者執行。
